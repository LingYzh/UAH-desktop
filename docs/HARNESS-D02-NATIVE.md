# D02 Windows execution helper

The independent `native/UAH.ExecutionHelper` console project targets `net10.0-windows`. It does not reference WPF, the old observation helper, Supervisor, or renderer APIs. The implementation requires Windows 10+ and a 64-bit process. Win32 structure sizes are checked before command creation; unsupported or failed job setup rejects execution without a direct-process fallback.

Build and validate from the repository root:

```powershell
dotnet build native/UAH.ExecutionHelper/UAH.ExecutionHelper.csproj -c Release --nologo
node --test tests/native/execution.test.mjs
npx tsx --test tests/runtime/execution-backend.test.ts
```

## Protocol v1

Each command result now includes optional `executionEvidence.provenance`: the capability-derived shell executable path and its observed executable file version (`shellVersionSource: executable_file_version`, not an inferred PowerShell engine version), the fixed invocation flags, actual working directory, timeout and output quota, `utf16le-base64` command encoding, and `raw_bytes_command_specific` output encoding. Missing legacy capability metadata is explicitly `unknown`.

Native capabilities and `CreateProcess` share the same shell path and flag constants. The encoded command argument is always represented as `[command recorded in tool invocation]` with `commandArgumentCapture: omitted`; the existing filtered tool invocation remains the sole logical command record. No Base64 command or duplicate command text is added. Known credentials are filtered from every provenance string before the result can enter SQLite or canonical records, and `redacted` records this loss of fidelity. Provenance is retained when a start acknowledgment is lost and when terminal evidence arrives; it does not imply successful creation, tree exit or output drain.

UTF-8 JSONL requests are `{ "id": "correlation-id", "method": "start", "params": { ... } }`. Responses are `{ "id": "correlation-id", "ok": true, "result": { ... } }`, or `{ "id": "correlation-id", "ok": false, "error": { "code": "...", "message": "..." } }`. A valid unique request id is retained on malformed-field errors. Unparseable frames, duplicate ids, and oversized lines may return a null id. Errors do not expose command content, exception traces, or environment values.

| Method | Parameters | Result |
| --- | --- | --- |
| `capabilities` | `{}` | Independent execution, atomic job assignment, no breakaway, redirected stdio, no interactive/PTY, unsandboxed, platform and size limits |
| `start` | `executionId` UUID; `command` PowerShell text, 1..8192 UTF-16 code units; `cwd`, `outputDirectory` existing absolute local directories; `timeoutMs` 1..120000; optional `maxOutputBytes` 1..67108864 (default 16777216) | Execution snapshot |
| `poll` | `executionId`; `stream` stdout/stderr; `offset` byte offset 0..67108864; `limit` 1..65536 | Raw bytes as base64, nextOffset, hasMore, snapshot |
| `wait` | `executionId`; `timeoutMs` 0..30000 | Current snapshot after completion or bounded waiting |
| `cancel` | `executionId` | Snapshot after at most five seconds waiting for exit/drain |
| `release` | `executionId` | `{executionId,status:"released",rawOutputRetained:true}` after confirmed terminal tree exit and output drain; closes owned handles and removes in-memory retention only |
| `shutdown` | `{}` | Snapshots for retained executions, then helper exit |

Unknown and duplicate fields, invalid scalar types, NULs, and out-of-range parameters are rejected. Request lines are bounded to 131072 characters and nesting depth eight. At most 64 requests, 16 live executions, and 128 currently retained executions are supported per helper. The retention limit produces a visible busy error; consumers must explicitly release confirmed terminal executions after retaining their results. There is no automatic eviction of live or unconfirmed executions. Capabilities advertise `terminalRelease:true` and `maxRetainedExecutions:128`.

`release` rejects live or unconfirmed executions with `execution_not_terminal` and unknown/released ids with `unknown_execution`. Repeated release is an error, not a fabricated successful acknowledgement. It closes only the execution's retained job/process handles; the stdout/stderr files remain intact. The helper removes the released item and keeps no unbounded UUID tombstone history. Protocol clients must generate a fresh execution UUID for every start. Retained ids cannot be reused; after release the Node adapter still prevents reuse through the existing dedicated output directory and exclusive mkdir. `outputDirectory` must be empty and dedicated; local directory ancestors cannot contain reparse points. Artifacts are opened with CreateNew.

Snapshots carry executionId, status (`running`, `completed`, `failed`, `timed_out`, `cancelled`), nullable reason/exitCode, jobAssigned, activeProcesses, treeExited, outputDrained, raw stdout/stderr paths and byte lengths, and elapsedMs. A command root exiting does not complete an execution while controlled descendants remain. Completed/cancelled/timeout results normally have activeProcesses=0, drained=true, and treeExited=true. Management or output failures can leave an unconfirmed tree certificate; consumers must inspect evidence rather than assume a status label proves exit. Cancel is idempotent after terminal completion and does not rewrite a previously completed outcome.

`wait` yields to asynchronous request handling, so a subsequent cancel can be processed while an earlier wait remains pending. Output pages are previews only and cannot stop a healthy execution. The shared stdout+stderr artifact quota is a hard byte limit: both pump writes are serialized, never exceed it, and explicitly terminate the job with reason output_limit when more bytes arrive. Wall-clock lifetime includes shell startup and all descendants. Timeout terminates the owned job and reports timed_out after exit/drain evidence.

## Ownership and Win32 boundary

CreateProcess uses STARTUPINFOEX with PROC_THREAD_ATTRIBUTE_JOB_LIST. Windows assigns the new root to its configured Job Object before its initial thread can run. There is no Process.Start→AssignProcessToJobObject gap in production. The helper checks IsProcessInJob against the retained job handle after creation. Job limits include KILL_ON_JOB_CLOSE and omit both BREAKAWAY_OK and SILENT_BREAKAWAY_OK. The job handle is noninheritable; the explicit HANDLE_LIST contains only NUL stdin and the stdout/stderr pipe writer handles. Pipe readers and job handles are excluded. Root process/thread, job, attribute allocations, pipe ends, and artifact streams have explicit owners and failure cleanup.

Tree management uses only the retained job/process handles. No WMI, process-name query, PID sweep, or process-tree reconstruction is used. QueryInformationJobObject BasicAccountingInformation must show zero ActiveProcesses, and both pipes must finish draining, before treeExited is true. EOF cancels owned jobs and closes them; abrupt helper termination causes Windows to close the noninherited job handle and kill the controlled tree. If a management query fails, the job closes fail-closed, and the helper does not fabricate a verified tree exit.

Official references used to verify the declarations and assignment contract:

- [Atomic process assignment with JOB_LIST](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812/).
- [UpdateProcThreadAttribute: JOB_LIST and HANDLE_LIST](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).
- [Job extended limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information), [basic limits and breakaway flags](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information), [basic accounting layout](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow).

## Node adapter

`src/runtime/execution-backend.ts` exports WindowsExecutionBackend with constructor `{helperPath?, dataDirectory}` and start/poll/wait/cancel/release/close. Each instance owns one helper and verifies its independent lifecycle and terminal-release capabilities before starting commands. Correlation ids are generated UUIDs. Responses are bounded to one MiB, pending requests are bounded, and helper protocol/identity/evidence errors reject pending work and close stdin. Helper stderr is consumed without exposing its bytes through adapter errors.

The adapter creates `dataDirectory/executions/<executionId>/` with exclusive mkdir and rechecks the directory ancestry for links. Callers cannot choose native output directories. Snapshot ids, byte counts, lifecycle certificates, and exact expected artifact paths are validated. Poll validates stream, offsets, base64 size and decoded byte count. Missing or incompatible helpers fail visibly with no direct shell fallback. Public ensureAvailable performs the handshake before the host marks possible command effects; once a start request is sent, a failed response cannot prove the command did not run.

The adapter's explicit release obtains fresh correlated terminal evidence, requires treeExited/outputDrained, validates the native release acknowledgement, then removes the Node evidence entry. Subsequent poll/wait/cancel/release fail as not owned, while raw files remain available by their recorded paths. `managedCommand` releases in finally only after terminal exit/drain confirmation and output processing. A failed artifact save also releases confirmed lifecycle handles while retaining original raw files for reconciliation; the outcome still reports RECORDING_FAILED. Unconfirmed lifecycle paths are retained for owned cancellation/shutdown and never released automatically. Release acknowledgement failure is visible and blocks a successful tool result.

close sends shutdown and EOF, awaits the owned ChildProcess close event, and verifies returned tree certificates. If shutdown times out, it reports an unconfirmed state. Once lifecycle capabilities were verified, it may terminate only its retained helper ChildProcess object to trigger KILL_ON_JOB_CLOSE; this is not an exit certificate and no process discovery is used. Default helper location currently points to the source tree's Release build. Packaged applications must pass a packaged helperPath explicitly; build/distribution integration belongs to the host.

The Electron host now passes the absolute `app.getAppPath()/native/UAH.ExecutionHelper/bin/Release/net10.0-windows/UAH.ExecutionHelper.exe` location through RuntimeClient options and worker argv[3] into Supervisor.executionHelperPath. The old NativeHelper observation path and behavior are unchanged. Windows buildDesktop builds the independent ExecutionHelper before bundling and stops when SDK startup/build fails. Desktop development already calls buildDesktop, so it uses the same gate. `npm run build:native` builds both observation and execution helpers; `build:native:execution` builds the independent execution helper alone. Non-Windows desktop builds skip this Windows-only native step and execution remains unavailable there.

This host path is valid for the current source-checkout desktop build. The repository has no installer/asar-unpack deployment pipeline. An executable inside app.asar cannot be launched directly; a distributable must include the complete helper Release output outside the archive and pass its actual absolute resources path. Current dotnet build is framework-dependent and requires the .NET 10 runtime; it is not a self-contained signed/native installer. This wiring does not claim packaged distribution validation.

## Limitations

This is redirected, noninteractive execution, with stdin mapped to NUL and absolute System32 WindowsPowerShell v1.0 powershell.exe using NoProfile, NonInteractive, and UTF-16LE EncodedCommand. It has no console/PTY/input API and does not support interactive or console-dependent programs. Requests for added console/interactive parameters are rejected; the helper cannot infer whether arbitrary PowerShell text will invoke a console-dependent application. The shell can still fail when such a program is invoked, and no interactive fallback is attempted.

Output preserves pipe bytes without transcoding except for configured known-credential matching described below. PowerShell may include its own CLIXML header/progress records in stderr; callers must not presume stderr is plain UTF-8 or that stdout/stderr have one global ordering. The 8192 command bound leaves room for base64 expansion beneath the Windows command-line limit. Artifact quota covers captured stdout/stderr bytes, not arbitrary files written by commands. Native artifacts are flushed to make pages readable; this is not a durable journal/SQLite ack or crash-proof fsync guarantee. Job ownership is lifecycle control, not a filesystem/network/credential sandbox. Link checks do not form an atomic sandbox against malicious concurrent filesystem mutation. These boundaries must retain the host's existing approval and UNSANDBOXED semantics.

## Known-credential output filtering

The helper now advertises `credentialFilter:true` and accepts optional start `redactSecrets`. Native validation allows up to16 printable ASCII values, each1–8192 bytes, aggregate65536; the Node adapter conservatively caps the aggregate at32768 to leave room in bounded IPC. Invalid settings or an old helper without this capability block commands before possible execution is recorded. Secrets are sent only through the owned helper IPC and are not added to protocol diagnostics.

Each pipe independently uses KMP matching and a bounded difference ring, retaining at most longest-key-minus-one pending bytes. Complete cross-read and overlapping matches are replaced before any spool write. Replacement is equal-length `*` bytes; if any configured credential contains `*`, all replacements use NUL so the replacement itself cannot retain or create an allowed ASCII credential. Other bytes remain unchanged, including binary data. Pending raw bytes count toward the combined output quota, while poll byte counts describe actual written output. Final drain flushes unmatched tails. This does not promise detection of unknown secrets, transformed encodings or values split across separate streams.

Snapshots report `outputRedacted`; a configured filter requires that boolean evidence on every lifecycle snapshot. Managed previews, public artifacts, range reads and both exports all use the already-filtered spool. `rawOutputRetained:true` remains the legacy release protocol field; when outputRedacted is true, retained files contain filtered bytes and original bytes are not retained. ToolOutcome records the flag; transcript capture conservatively becomes partial. Hashes identify saved filtered bytes, never the missing original. Filtering configuration alone does not lower coverage when no match occurs. Request policy is now `uah-journal-v2`.

Two actual Supervisor/native/SSE privacy regressions pass: known canary absent from memory previews, next request tool results, canonical records, stdout/stderr artifacts, UTF-8/base64 range reads, full/share exports and release/shutdown spools; nonmatching six-byte non-UTF8 output remains exact with complete coverage. Node boundary tests also cover missing/false capabilities, invalid inputs and malformed filtering evidence. Earlier raw-output observations above refer to unfiltered fixtures.
