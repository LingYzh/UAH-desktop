# D07 context and task-tree budget foundation

## Current policy — 2026-10-04

Cumulative estimated/provider-reported token usage is accounting only and never stops a task, request, or tool. The former 4,000,000-token cap and token-overrun admission checks have been removed. New snapshots use `limits.maxEstimatedTokens: null` and `estimatedTokensExceeded: false`. Legacy numeric options are accepted but do not impose a cap; valid older snapshots (including exceeded ones) restore their counters with the token limit disabled. Counters saturate safely at the maximum representable integer without blocking execution. Existing stopped tasks remain historical records and may be explicitly resumed; no request or tool is automatically replayed.

Single-request context-capacity admission and the request/tool/time/concurrency limits remain separate. Recovery no longer grants or displays a cumulative token allowance. The earlier implementation and validation notes below describe historical checkpoints; references there to token limits, token-overrun stops and token grants are superseded by this policy.

`src/runtime/context-governor.ts` is a pure admission/accounting module. It performs no network requests, persistence, provider retry or history compression. Supervisor now supplies integration: root and descendant operations share one task-tree budget, canonical `context.admission` and `budget.updated` events retain decisions/accounting, and a programmatic `SupervisorOptions.taskBudget` can override limits. Cancellation, deadline handling and execution authorization belong to that integration.

## Complete context admission

`assessContext({ instructions, history, tools, capacity?, maxOutputTokens? })` serializes the complete JSON object containing those three content fields and measures its UTF-8 byte length. Native tool blocks, opaque signatures, encrypted reasoning and tool results all count. Nothing is removed, rewritten, shortened or mutated. Values that JSON would silently omit or coerce are rejected: undefined, non-finite numbers, bigint, functions, sparse arrays, accessors, hidden fields, non-plain objects and cycles. Nesting is bounded at 128 levels. Configuration fields are strict, with positive safe-integer capacity/output limits; output may also be null/omitted.

The input estimate is one byte per estimated token plus 1024 tokens of wrapper allowance. This is a conservative admission estimate, not a tokenizer, provider billing measurement or receipt. With known capacity, the module reserves explicit `maxOutputTokens`, otherwise `min(8192, floor(capacity * 0.2))`; tool allowance is `min(8192, floor(capacity * 0.1))`; error allowance is `ceil(capacity * 0.05)`. Admission requires the sum to fit capacity, including equality. The result reports `bodyBytes`, `inputEstimatedTokens`, `wrapperTokens`, `outputReserve`, `toolReserve`, `errorReserve`, `requiredTokens`, `capacityKnown`, `capacity`, `bodyByteLimit`, `admitted` and a reason code.

Unknown capacity admits only a JSON body of at most 16 MiB. The result explicitly reports `capacityKnown: false`, `capacity: null` and `capacity_unknown_body_within_limit` or `body_bytes_exceeded`. It makes no claim that this body fits an unknown provider context window. No inferred capacity is substituted.

## Shared task-tree accounting

One `TaskTreeBudget` instance can be shared by a root task and its descendants. Defaults are 64 requests, 256 tool calls, 30 minutes elapsed, 4,000,000 estimated tokens and four concurrent requests. Limits are configurable; tools/token capacity may be zero to forbid that resource. The default clock is `performance.now()`, and tests/callers can inject `monotonicNow`. Invalid/backwards clocks fail instead of extending the deadline.

`reserveRequest(estimatedTokens)` atomically checks elapsed time, charged tokens, request count and concurrency; it returns a random UUID reservation and immediately charges the estimated tokens and one request while occupying an in-flight slot. Rejection consumes no counters. `settleRequest(id, reportedTokens)` releases the slot and charges `max(reserved, reported ?? reserved)`. It never refunds an estimate or request count, including cancellation or unknown usage. A reservation can settle only once; invalid settlement preserves the live reservation.

Reported overrun is retained in the snapshot and does not throw during settlement: it must not replace an already observed provider response or error with a budget error. `check()` then rejects elapsed/token overruns before further effects; both request and tool reservation methods invoke that check. Extremely large valid reported aggregates saturate at `Number.MAX_SAFE_INTEGER` and permanently mark `estimatedTokensExceeded`, so arithmetic cannot wrap into renewed admission. Settlement remains possible after the elapsed deadline to preserve completion facts.

`reserveTools(count)` checks a whole batch before charging any tool count. `BudgetExceededError.code` identifies `requests`, `tools`, `elapsed_ms`, `estimated_tokens`, `concurrent_requests` or the integration's `context_capacity` rejection. `snapshot()` returns request/tool counts, charged tokens, currently reserved tokens, in-flight count, elapsed time, token overrun flag and a copied limits object. A snapshot is evidence of accounting, not authorization for execution.

## Tool correction and no-progress accounting

ToolProgressGovernor now counts failed/denied tool batches separately from network retries. A run pauses after six failed batches, or after three consecutive identical all-failed batches without side effects. The fingerprint covers ordered tools, canonical JSON arguments (raw fallback for invalid/deep arguments), error/exit/effect state, resource versions, artifact references and complete result content. Wall-clock and execution identities do not affect equality. Successful, cancelled or potentially effectful results break the repetition streak; cumulative failure counts remain charged. This is a bounded failure heuristic, not proof that the user's goal has made no progress.

Each batch is observed only after durable tool results. `progress.updated` and Run.toolProgress commit together before another request. A failure of that commit stops with recording_failed. The two stop codes are no_progress and model_corrections, with the existing stopped/suspended_budget display. New accepted steering resets the repetition streak at the safe application boundary but does not refund failures. The runtime does not automatically re-execute a tool; a subsequent tool invocation is always a new model call subject to existing permissions, version checks and journal admission. Unknown tool names still fail immediately at the protocol boundary, before this counter.
