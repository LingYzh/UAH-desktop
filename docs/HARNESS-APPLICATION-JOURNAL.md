# Application connection-test ledger

Connection tests initiated from the endpoint settings are real model requests. The worker now records them in an independent `dataDirectory/application-journal/runtime.sqlite` authority and its corresponding journal/artifact projection. Model discovery remains its existing GET operation and does not create a token usage entry. The exported compatibility transport `testApiConnection` remains unchanged; desktop worker connection tests use ApplicationJournal.testConnection.

Every admitted test receives fresh operation, turn, request, attempt, and step identities. Its usage has `purpose: connection_test` and `scope: { kind: application }`; provider counts remain nullable when unknown, including failure and cancellation. Tests do not count as user conversation requests, Agent runs, or delegated work. They do not appear in Supervisor's store or UI snapshots and have no parent/child relationship.

The v1 journal envelope requires RunIdentity and a session partition to index its events. The independent store therefore uses the technical partition id `application` and technical RunRecord ids as operation indexes. This is a compatibility representation, not a fabricated user session or session-scoped usage. The synthetic row is confined to the application store and is not a user conversation. Scope and purpose are the authoritative interpretation when combining usage data.

The probe uses streamAgentApi with no tools, the fixed prompt `Reply with the single word OK.`, default model parameters overridden to a 256-token output request cap and a 30-second request timeout. It records accepted operation text, state, request preparation before network dispatch, exact application payload, provider frames, normalized usage snapshots, public text, native continuation, and terminal states through the same RequestJournal and RunJournal boundaries as other API requests. No network retry is performed. Unsupported tool calls or responses with no visible text fail the connection check. If provider response parsing completes and subsequent probe validation fails, the provider terminal remains truthful and the application operation receives a failed state.

Returned text is limited to an 8192-character preview plus an explicit truncation marker. This display limit does not truncate the recorded local response. Provider-native frames and request snapshots remain restricted artifacts, and known endpoint credentials—including secrets split across streamed text—are removed before canonical event, SQLite, or file persistence. The settings' existing credential store remains the owner of actual API keys; the application ledger does not copy connection objects or authentication headers.

Authority/artifact recording failures block a new send and latch further application-probe admission closed for that worker. The persisted `recording_failed` boundary also blocks new probes after restart. Healthy transient HTTP/provider errors produce failed attempts with unknown or reported usage; they do not disable later explicitly requested probes. Already-aborted calls can record unknown/cancelled attempt evidence without a network send. Closing requires callers to abort and await active probes; the worker aborts its probe controllers, awaits their tasks, then closes the application journal during shutdown.

On restart, unfinished application operations receive a single recovery transaction with `run.state: cancelled`, legacy `state: stopped`, a sequence increment, finish timestamp, and an explicit process-restart stop reason saying completion was not observed. Existing completed/failed/cancelled operations and recording-failure boundaries remain unchanged. Recovery does not fabricate a provider terminal or token counts, change prior request/usage facts, or send any network request. Its run terminal does not close an unfinished provider attempt: transcript coverage can therefore remain partial. Subsequent restart is idempotent.

`tests/runtime/application-journal.test.ts` uses only isolated temporary stores and local HTTP/SSE fixtures. Its seven tests pass for all three protocols, verifying the serialized 256-token cap, application scope/purpose, normalized usage, intent/frame/native persistence, offline validation, absence of user-store sessions, HTTP failure, empty/tool responses, cancellation before and after dispatch, no implicit retry, bounded UI preview with full local content, split-secret removal from every persisted file, and fail-closed admission after recording failure including restart. The recovery fixture has an unfinished dispatch plus a completed operation; it checks unchanged historical facts, one appended recovery state, sequence advancement, preserved completed operation, no fabricated provider terminal/network call, and idempotent second restart. TypeScript typecheck passes. Final transport/RequestJournal and desktop endpoint integration validation is reported with the task's overall checks.

Combined application/RequestJournal/API transport/model-history regression passed 57/57 after the recovery addition; typecheck passed. Production build passed before this final recovery change. The endpoint Electron fixture subsequently added explicit Agent/permission/reasoning choices required by the current composer.
