命中率按同一次尝试的输入与缓存字段配对后求总和相除，**不是各请求百分比的平均值**。失败或重试中缺失的 usage 不补零，因此上述百分比不能冒充全会话的精确覆盖。界面会显示百分比及“已上报 54/57 次尝试”一类说明；字段齐全时才显示完整会话比例。DS 未报告缓存写入字段，与输入/缓存读取是否已知是不同的覆盖问题。

这些是本次隔离会话的服务响应统计，没有将 DS 后台自然日／账号总量当成相同范围。计费重试的缺失用量只能由 provider 补足，客户端不能猜测。缓存比例也受服务缓存已有状态影响，不保证任何未来会话都达到该比例。

## 前缀与恢复

- 两组正常 coding 测试的系统指令和工具定义 hash 始终一致。
- DS 主请求相邻比较 55 次保持原前缀，1 次在超时后的续接发生 `history_or_route_changed`，最早差异位于 `history[56]`。
- 公司主请求相邻比较 111 次保持原前缀，1 次在停止后的明确续接发生历史重建，最早差异位于 `history[119]`。
- 没有发现记忆更新导致系统头逐轮变化；上述历史重建与失败恢复相关，不能把它描述成所有请求都完全 append-only。
- root 独立运行生成项目的完整测试，并直接执行两套 CLI 的样例 `inspect`；均报告 4 条记录，note 列 3 个非空、1 个空值。DS 的 `filter status=active` 正确保留 3 条记录及带换行的引用字段。

## 容量压力专项

另一份公司端点隔离会话先设 32K、再设 48K 测试窗口，实际模型容量配置没有改动。共 53 次尝试（含 7 次摘要），观察到 3 次原子压缩提交：历史原件分别从 108,344→31,538、117,255→39,674、123,995→46,272 bytes。压缩后确实继续执行了真实文件工具。4 个未满足缩减条件的候选回滚；最终无法安全缩到测试容量内时保留证据并停止。这是恢复与拒绝行为的验收，不是宣称 48K 下整个项目也全部完成。

该组已有配对报告的 52/53 次尝试，缓存命中率 82.19%。摘要使用独立上下文，压缩会改变历史前缀，因此这组不应和不压缩的正常会话直接比较。工具／系统头仍稳定，主请求有 2 次已记录的历史首部变化。

真实验收促成两处修正：有效 provider 输入用量不再因低于粗略 JSON 估算的一半而被拒绝；已经超限时总会检查压缩，25% 请求体增长阈值只限制提前压缩频率。校准仍要求 header 与完整历史前缀一致，压缩后清除旧基准。

## 失败记录与限制

- 最初测试夹具禁止 shell，却没有创建 `src/tests` 父目录，造成模型无法继续创建文件。补齐目录后，使用明确的新用户步骤续接；原始失败报告保留。0 个测试不算通过。
- 公司模型曾漏传新文件必需的 `expectedContent:null`，达到既有的工具纠错次数上限。明确补充正确契约后续接，最终有真实成功补丁和测试。没有取消该安全边界，也没有恢复累计 token 限制。
- DS `deepseek-flash` 与额外探索的 `deepseek-v4-pro` 曾在默认 60 秒 HTTP 响应期限内超时。之后正常长测试仅在 runner 内覆盖 `timeoutSeconds=600`；真实端点默认值未改。Pro 探索仅 4 次尝试、没有完成 coding 步骤，不算验收通过。
- runner 最初使用日志 UI 的最近 100 条列表与每请求 1000 事件截断视图，长会话统计会不完整。已改为直接读取完整 accounting/dispatch/intent 投影；最终报告覆盖公司 113 次尝试，没有截掉前 13 次，也不逐请求反复解析全部流式正文。
